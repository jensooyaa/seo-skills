# 元信息规则表

面向 `lib/check-page.js` 的元信息组，共 10 条。体例与 `rules-semantic.md` 一致：
每条给出脚本判定条件、级别、报告文案与已知边界。

> **实现进度：10 条全部实现**，用例在 `tools/cases/meta-*.html`。

**这份表既是实现依据，也是报告文案的来源** —— 脚本只输出「命中了哪条规则 + 命中的证据」，
报告里的「为什么」「怎么改」一律从本表查得，不由模型现编。

---

## 长度一律按「半角当量」算，不按字符数

title 和 description 的长度阈值，**全角字符算 2、半角字符算 1**。

原因：**Google 是按像素宽度截断的，不是按字符数。** 一个汉字的显示宽度约等于两个
英文字母，所以「30 个汉字」和「60 个英文字母」在搜索结果里占的位置差不多。按字符数
算的话，中文页面会被判成「太短」而英文页面被判成「太长」，两头都错。

本表里凡是写「显示宽度」的地方，指的都是这个半角当量。

---

## 脚本输出字段

与语义化组完全一致，`group` 固定为 `元信息`：

```json
{
  "rule":     "title-length",
  "group":    "元信息",
  "level":    "建议",
  "detail":   "title 显示宽度 78，超出建议上限 60，搜索结果里会被截断",
  "evidence": ["<title>…</title>"],
  "count":    1
}
```

## 1 · title-missing

| | |
|---|---|
| **判定** | `head` 里没有 `title`，或 `title` 内容 trim 后为空 |
| **级别** | 阻断 |
| **detail** | `页面没有 title` / `页面的 title 是空的` |
| **evidence** | 有第一个 h1 时给出它，提示「标题该写什么」 |

**为什么**：title 是搜索结果里那行蓝色标题，也是搜索引擎判断页面主题最强的信号。缺失时 Google 会自己从正文里挑一段来充数，挑出来的往往是导航文字或者品牌名，点击率会明显变差。

**怎么改**：在 `<head>` 里加 `<title>`，写「本页主题 + 品牌名」，主题在前品牌在后 —— 搜索结果里前面的字更容易被看到，而且长了会从尾部截断。

**边界**：只看 `head` 里的 `title`。页面正文里内联 SVG 的 `<title>` 是图形的无障碍标题，与本条无关，不参与判定。

---

## 2 · title-length

| | |
|---|---|
| **判定** | 显示宽度 < 15 或 > 60 |
| **级别** | 建议 |
| **detail** | `title 显示宽度 N，低于建议下限 15，信息量不足` / `title 显示宽度 N，超出建议上限 60，搜索结果里会被截断` |
| **evidence** | title 原文 |

**为什么**：太短说明没写够，白白浪费了搜索结果里最显眼的位置；太长会被截断，被截掉的那部分等于没写，而很多人恰恰把品牌名和关键词放在了尾巴上。

**怎么改**：控制在显示宽度 15~60 之间（约 15~30 个汉字，或 15~60 个英文字母）。把最重要的词放前面。

**边界**：
- 60 是**建议上限不是硬上限**。Google 实际按像素截断，不同字符宽度不同，60 只是个稳妥的经验值，超一点点不必大动干戈。所以本条级别是「建议」。
- title-missing 已命中时本条不重复报（空标题不需要再说一遍「太短」）。

## 3 · description-missing

| | |
|---|---|
| **判定** | `head` 里没有 `meta[name=description]`，或 content trim 后为空 |
| **级别** | 警告 |
| **detail** | `页面没有 meta description` / `meta description 的内容是空的` |
| **evidence** | 无 |

**为什么**：description 是搜索结果里标题下面那两行说明。它**不是排名因素**，但直接决定点击率 —— 缺失时 Google 会从正文里自动摘一段，摘出来的经常是导航栏、Cookie 提示这种毫无吸引力的内容。

**怎么改**：加 `<meta name="description" content="…">`，用一两句话说清「这页能解决什么问题」，把用户会搜的词自然地放进去。

**边界**：级别定「警告」不是「阻断」—— 它不影响收录，只影响点击率。

---

## 4 · description-length

| | |
|---|---|
| **判定** | 显示宽度 < 50 或 > 160 |
| **级别** | 建议 |
| **detail** | `description 显示宽度 N，低于建议下限 50，信息量不足` / `description 显示宽度 N，超出建议上限 160，搜索结果里会被截断` |
| **evidence** | description 原文 |

**为什么**：同 title —— 超出的部分在搜索结果里看不见，等于没写。

**怎么改**：控制在显示宽度 50~160 之间（约 25~80 个汉字）。把最有说服力的一句放最前面。

**边界**：description-missing 已命中时本条不重复报。

## 5 · canonical-missing

| | |
|---|---|
| **判定** | `head` 里没有 `link[rel=canonical]` |
| **级别** | 警告 |
| **detail** | `页面没有 canonical` |
| **evidence** | 无 |

**为什么**：canonical 告诉搜索引擎「同样的内容有好几个 URL 能访问到，请以这个为准」。没有它，带 `?utm_source=` 的分享链接、带不带尾斜杠的两个地址、大小写不同的路径，都可能被当成几个互相重复的页面 —— 权重被摊薄，而且引擎会自己挑一个当代表，挑中的不一定是你想要的那个。

**怎么改**：每页加 `<link rel="canonical" href="该页的标准绝对 URL">`。写绝对地址，不要写相对路径。

**边界**：无。

---

## 6 · canonical-multiple

| | |
|---|---|
| **判定** | `head` 里 `link[rel=canonical]` 多于一个 |
| **级别** | 警告 |
| **detail** | `页面有 N 个 canonical` |
| **evidence** | 每个 canonical 的 href |

**为什么**：Google 的明文规定是「出现多个 canonical 时，全部忽略」。也就是说多写一个不是多一层保险，而是**一个都不生效**，等于回到了没有 canonical 的状态。

**怎么改**：只留一个。最常见的成因是模板层已经输出了一个，页面组件又输出了一个 —— 检查一下有没有两处代码都在写。

**边界**：无。

---

## 7 · canonical-mismatch

| | |
|---|---|
| **判定** | canonical 归一化后与当前页面 URL 归一化后不相等 |
| **级别** | 警告 |
| **detail** | `canonical 指向了另一个地址` |
| **evidence** | 当前 URL、canonical 值、以及归一化后的两个地址 |

**为什么**：canonical 指向别处，等于主动告诉搜索引擎「这页不用收录，去收那个」。如果那是刻意的（分页归一到首页、多个筛选态归一到列表页），没问题；**如果是模板写错了**（比如所有详情页的 canonical 都写死成了首页），整批页面会集体从索引里消失，而这种错误从页面上完全看不出来。

**怎么改**：确认这是不是有意为之。不是的话，把 canonical 改成本页自己的 URL。

**边界**：这是元信息组里**最容易误报的一条**，刻意收窄了五处 ——

| 情形 | 报不报 | 为什么 |
|---|---|---|
| 只差 `utm_source` 等追踪参数 | **不报** | 把追踪参数归一掉正是 canonical 的正当用法，报它是纯误报 |
| 只差尾斜杠（`/a` vs `/a/`） | **不报** | 同一个页面的两种写法 |
| 只差 `www.` 前缀 | **不报** | 站点选一个主域名做规范，是标准做法 |
| 只差协议（http / https） | **不报** | 归一到 https 是标准做法 |
| 差 `page=2` 这类会改变内容的参数 | **要报** | 第 2 页归一到第 1 页会让第 2 页的内容整个丢掉 |
| 没有传入页面 URL | **不报** | 没有对照物，无从判断 |

⚠️ **`<base href>` 有个坑**：页面可以用 `<base href="//cdn.example.com/">` 声明相对路径的基准，而这个值本身可能是**协议相对**的。直接拿它当 `new URL(href, base)` 的 base 会抛异常，把一个完全合法的 canonical 误报成「不是合法的 URL」。**必须先把 base 自己对着页面 URL 解析一次**，拿到绝对地址再用（用例 `meta-10`）。

## 8 · lang-missing

| | |
|---|---|
| **判定** | `html` 标签没有 `lang` 属性，或值 trim 后为空 |
| **级别** | 警告 |
| **detail** | `<html> 缺少 lang 属性` |
| **evidence** | html 的开标签 |

**为什么**：`lang` 告诉搜索引擎和读屏软件这页是什么语言。缺失时引擎只能靠正文猜，中英混排的页面尤其容易猜错 —— 猜错会影响它把这页投给哪个语种的用户，也会让浏览器的「翻译此页」提示行为异常。

**怎么改**：`<html lang="zh-CN">`（简体中文）或 `<html lang="en">`。用 BCP 47 标准写法。

**边界**：只检查有没有、空不空，**不校验值是否为合法的语言标签**。`lang="zh_CN"`（下划线，错的）这种写法本条抓不到。

## 9 · viewport-missing

| | |
|---|---|
| **判定** | `head` 里没有 `meta[name=viewport]` |
| **级别** | 警告 |
| **detail** | `页面没有 meta viewport` |
| **evidence** | 无 |

**为什么**：没有 viewport，手机浏览器会按桌面宽度（通常 980px）渲染再整体缩小，正文小到看不清。Google 用的是移动优先索引 —— **它主要看你的手机版页面来决定排名**，这一条不满足会直接判定为「移动设备易用性有问题」。

**怎么改**：`<meta name="viewport" content="width=device-width, initial-scale=1">`。

**边界**：只检查存不存在，**不校验 content 的内容**。`user-scalable=no`（禁止缩放，无障碍上不推荐）这种本条抓不到。

## 10 · og-incomplete

| | |
|---|---|
| **判定** | `og:title` / `og:description` / `og:image` 三个里缺任意一个 |
| **级别** | 建议 |
| **detail** | `页面没有 Open Graph 标签，分享到社交平台时没有卡片` / `Open Graph 缺少：og:image` |
| **evidence** | 已有的 og 标签 |

**为什么**：Open Graph 决定链接被分享到微信、飞书、Slack、Facebook 时长什么样。缺失时对方只能看到一条光秃秃的 URL，点击率差很多。它不直接影响搜索排名，但影响外部链接带来的流量。

**怎么改**：在 `head` 里补齐三个：

```html
<meta property="og:title" content="…">
<meta property="og:description" content="…">
<meta property="og:image" content="https://…/og.jpg">
```

`og:image` 用绝对 URL，建议 1200×630。

**边界**：
- 只查这三个必需项。`og:url` / `og:type` / `og:site_name` 是推荐项，不查。
- **不校验 og:image 那个地址能不能打开**，那要多发一个请求，成本和收益不成正比。
- Twitter Card（`twitter:card` 等）不查 —— 缺失时 Twitter 会回退到读 og 标签，补齐 og 就够用了。

## 已知盲区

| 盲区 | 影响的规则 | 原因 |
|---|---|---|
| 不校验语言标签合法性 | lang-missing | `lang="zh_CN"` 这类写错的值抓不到 |
| 不校验 viewport 的内容 | viewport-missing | `user-scalable=no` 抓不到 |
| 不请求 og:image | og-incomplete | 图片是不是 404、尺寸对不对，都不知道 |
| 只看服务端 HTML | 全部 | 靠 JS 动态塞进 head 的 meta 标签看不到。**这条对 SPA 尤其要紧** —— 很多站的 meta 是 `react-helmet` 之类在客户端写的，服务端 HTML 里一个都没有，而 Google 第一波抓取看到的正是服务端 HTML |
