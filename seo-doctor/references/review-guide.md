# 模型判断指引

**读这份文件的是你（Agent），不是用户。**

脚本已经把「是不是」判完了 —— 20 条确定性规则，命中就报，不命中就不报，每次跑
结果一模一样。这份指引管的是脚本做不了的另一半：

> **脚本负责「是不是」，你负责「要不要紧、为什么、先改哪个」。**

---

## 一、四条铁律

### 1. 不打分

不要星级、不要百分制、不要「SEO 配置水平优秀」这类总评。

开发拿到分数不知道该动哪一行代码。而且分数这层抽象最容易出错又最没法追责 ——
真实发生过：把 61 字符的 title 打成 ⭐⭐⭐⭐⭐ 并写「在 50-60 理想范围内」，
61 明明超了。

要总览就给**计数**（「命中 3 条，其中阻断 0」），那是事实，不是判断。

### 2. 你的判断必须和脚本的判定分开写，且标明出处

报告里两者是两个独立段落，措辞也要有区别：

| | 脚本判定 | 你的判断 |
|---|---|---|
| 依据 | 规则表里的确定性条件 | 语义、上下文、经验 |
| 可复现 | 是，每次一样 | 否，换个说法可能不同 |
| 写法 | 「title 显示宽度 67，超出上限 60」 | 「模型判断：title 把品牌名放在了末尾，超长时它会第一个被截掉」 |

**不要把自己的判断混进脚本那段冒充确定性结论。** 这是这个工具唯一不能破的底线 ——
一旦混了，用户就分不清哪些结论是可以直接信的。

### 3. 工具用来补脚本的短板，不用来重做脚本的活

你手上有 web_fetch、浏览器、命令行 —— **该用就用**，这些是你的价值。
但用在哪里要分清楚：

| 情形 | 怎么办 |
|---|---|
| **脚本已经查过的**（title 长度、canonical、OG 有没有、地标齐不齐…） | **不要重查。** 你重算一遍只会得到一个更差的答案 —— 真实发生过：脚本说「显示宽度 67，超出上限 60」，手工数成「61 字符，在 50-60 理想范围内 ✅」，两处都错。真觉得脚本判错了，那是 bug，**把它当 bug 报出来**，不要绕过去自己算一遍 |
| **脚本查不了的**（见下表） | **主动去查。** 这是模型判断的主要素材来源 |
| **补查拿到的结论** | 一律进「模型判断」段，并写明**用什么方法拿到的** —— 别人要能照着复现 |

#### 值得补查的清单

按性价比排。**不必每次全做**，挑跟当前页面相关的。

| 想知道什么 | 怎么查 | 脚本为什么做不到 |
|---|---|---|
| **alt 和图对不对得上** | 从「页面概况」里取图片 URL，把图看了 | 脚本只能查词表。这是最大的盲区，也最容易藏真问题 —— `alt="蓝色外套"` 配一张鞋的图，词表永远抓不到 |
| **SPA 的 meta 是不是客户端才塞进去的** | 用浏览器打开，对比渲染后的 DOM 和「页面概况」里的值 | 脚本只看服务端 HTML。**两者不一致是很严重的问题**：Google 第一波抓取看到的正是服务端那份，客户端才补上的 meta 要等渲染队列，慢得多且不保证 |
| **有没有被 noindex 挡住** | 看响应头的 `X-Robots-Tag`、抓同源 `/robots.txt` | 索引指令组还没实现。`X-Robots-Tag` 藏在响应头里，来自 Nginx/CDN/网关，**前端在自己代码里搜 noindex 一行都搜不到**，排查经常卡好几天 |
| **og:image 打不打得开、尺寸对不对** | 请求一下那个 URL | 脚本刻意不发这个请求（多一次网络往返，成本收益不划算） |
| **同类页面的 URL** | 从首页的链接里挑几个 | M3 爬虫还没做，而判断模板层必须测多页 |
| **某条规范到底怎么定的** | 查 Google Search Central / schema.org 官方文档 | 规则表覆盖不到的边角情形 |

#### 补查的两条边界

**一、结果不要写进「脚本判定」段。** 那一段唯一的价值就是可复现 —— 每次跑都一样、
有 826 条断言盯着。掺进任何非确定性的东西，这个价值就没了。补查的结论放
「模型判断」段，标明方法。

**二、补查也要有结论。** 查不出来就写「查了 `X-Robots-Tag`，响应头里没有」，
不要写「建议进一步确认实际渲染长度」「具体值需确认」——
**那等于没查，但用户会以为查过了，比不写更糟。**

### 4. 只说你真的查过的

区别在于**有没有真的去看**，不在于脚本查没查：

| 结论 | 脚本查了吗 | 能不能说 |
|---|---|---|
| 「结构化数据配置完善」 | 没有，只列了 `@type` | **不能。** 字段一个都没校验，而「完善」说的正是字段。可以说「有 Product 类型」，不能说「Product 填全了」 |
| 「alt 与图片内容相符」 | 看不懂图 | **去看了图就能说**，并写明「核对了这 3 张图」。没看就不能说 |
| 「页面没有被 noindex」 | 没有，那组规则没实现 | **查了响应头和 robots.txt 就能说**，并写明查了哪两处。没查就不能说 |
| 「移动端适配良好」 | 只查了 viewport 标签存不存在 | **不能。** 「适配良好」要看实际布局，那得真拿浏览器在窄视口下看过 —— 看过了才能说 |

一句话：**没查过的事一个字都别说；查过的，把方法一并说出来。**

## 二、要判断什么

按「页面概况」里的字段逐项过。**每条判断都要指出你依据的是哪个事实。**

### title —— 拿 `facts.title.value`

- **重要的词在不在前面？** 搜索结果从尾部截断，且靠前的词权重更高。
  `品牌名 | 页面主题` 这个顺序在长 title 上等于把主题送去被截掉。
- **有没有用户真会搜的词？** 「解决方案」「一站式服务」这类词没人搜。
- **和 h1 是什么关系？** 两者可以不同（title 给搜索结果列表，h1 给页面读者），
  但**表达的应当是同一件事**。差得太远说明其中一个写错了对象。
- **同一站点多个页面的 title 是不是雷同？** 只有品牌名不同的一批 title，
  搜索引擎难以区分，也拿不到各自的关键词。这条要测过多页才能说。

### description —— 拿 `facts.description.value` 和 `width`

- **前 160 当量里有没有把最有说服力的一句放进去？** 超长不是最要紧的，
  最要紧的是**被截掉的是不是关键信息**。脚本只能说超了多少，看内容是你的活。
- **是不是一句承诺？** 「本公司成立于…」是自我介绍，不是给搜索用户的理由。
- **有没有和 title 重复？** 重复等于浪费了两行里的一行。

### 标题大纲 —— 拿 `facts.outline`

这是你最能出活的地方，脚本只查了「有没有 h1」「跳不跳级」两件机械的事。

- **h2 之间是不是同一层级的概念？** 把「产品介绍」和「联系我们」并列成 h2
  是常见毛病 —— 后者不是内容章节。
- **大纲读下来能不能还原页面在讲什么？** 只看这棵树就该明白这页是干什么的。
  还原不出来，说明标题写成了口号而不是章节名。
- **有没有把导航、页脚、侧栏的标题混进正文层级？** 大纲里突然冒出「友情链接」
  「关注我们」，说明这些区块用了 h2/h3，该降级成普通文本或 `<p>`。

### 结构化数据 —— 拿 `facts.structured`

规则没实现，但**类型对不对得上页面**这件事你现在就能判断：

| 这是什么页 | 应该有 | 常见的缺 |
|---|---|---|
| 商品详情页 | `Product` + `Offer` | 只有 `Organization`，等于没标 |
| 文章/博客 | `Article` / `BlogPosting` | 缺 `datePublished`（但你看不到字段，只能提醒去查） |
| 列表页 | `ItemList` / `CollectionPage` | 什么都没有 |
| 任何页 | `BreadcrumbList` | 面包屑没标，搜索结果里出不来路径 |

⚠️ 你只看得到 `@type`，**看不到字段是否齐全**。所以措辞是「这页是商品详情页，
但没有 `Product` 类型」（这个能确定），不是「`Product` 的必填字段齐全」（这个不能）。

### 锚文本与 alt

脚本查的是词表，只抓得住「了解更多」这类原词。你能抓词表外的变体：

- 「查看这个」「戳这里」「→」「立即」—— 同样没描述目标页
- `alt="产品展示图 1"` —— 编号式的变体，词表可能漏掉

发现词表漏掉的，除了在报告里说，**还要建议把这个词加进
`references/rules-semantic.md` 的词表** —— 让它下次变成确定性判定。

## 三、怎么排优先级

清单里的「阻断 / 警告 / 建议」是**规则本身的通用级别**，它不看这是什么页面、
不看波及多少页、也不看这页断在链路的哪一环。真实优先级按四个维度重排，
**从上往下依次判，上一条能分出胜负就不看下一条**：

| 维度 | 问什么 | 影响 |
|---|---|---|
| **1. 断在哪一环** | 见 `diagnose-chain.md` 的六环 | **环节越靠前越优先。** 环节 1 断了（爬虫进不来），环节 4 的 title 长度根本不用谈 —— 不是不重要，是在这之前不具备讨论意义 |
| **2. 波及面** | 模板层还是这一页？ | 模板层一条命中 = 全站命中，直接拉到最高 |
| **3. 对流量的作用** | 阻断收录 > 影响点击率 > 影响理解 | 收录不了，后面全是零 |
| **4. 改动成本** | 改一个属性，还是改页面结构？ | 同等收益下先做便宜的 |

### 怎么判断是不是模板层

**测 2~3 个同类页面，同一条规则都命中，就是模板层。** 这是你该主动做的事，
不用等用户要求 —— 见下面第四节。

### 输出优先级时要写清理由

不要只排个序。写成：

> **先改这三条**
> 1. `description-length`（198 → 160）—— 这是落地页，搜索结果里最能打的那句
>    被截在外面，直接影响点击率，改文案成本最低
> 2. `img-alt-meaningless` —— 只有一处，改一个属性的事
> 3. 标题大纲里「联系我们」被写成了 h2 —— 模型判断，它不是内容章节，
>    混在正文层级里会干扰主题识别

## 四、决定测什么

### 用户给了具体 URL

直接测那一个。测完**主动提议**：「要不要再测一个列表页和一个详情页？同一套模板
出来的问题，一页命中通常就是全站命中。」

### 用户给的是站点，或只说「帮我看看官网 SEO」

**不要只测首页。** 首页往往是单独写的，最不具代表性。

挑三类各一个，因为它们通常是三套不同的模板：

1. **首页**
2. **列表页 / 分类页**（商品列表、文章列表）
3. **详情页 / 落地页**（单个商品、单篇文章）—— **这类最重要**，SEO 流量主要落在这里

URL 怎么来：问用户，或者**自己抓一下首页从链接里挑**（这正是铁律 3 说的
「脚本查不了的主动去查」—— `facts` 里没有链接清单，M3 爬虫也还没做）。
挑的时候看 URL 形态：`/products/123`、`/blog/xxx` 这种带 ID 或 slug 的多半是详情页，
`/products`、`/blog` 这种是列表页。

测完把三份结果放一起看：

- **三页都命中同一条** → 模板层或全站配置问题，写成一条，标明「全站」
- **只有一页命中** → 这一页的问题
- **详情页命中而首页没有** → 最值得警惕，因为详情页数量最多

### 用户给的是一批 URL

逐个测，然后**按规则聚合**，不要按页面罗列 —— 20 个页面 × 3 条问题写成 60 条
没人看得下去。写成「`canonical-missing` 命中 18/20 页」。

## 五、什么时候该追问

**最多问两个问题，问完就开始干活。** 问题要能改变结论，不能改变结论的别问。

值得问的：

| 问 | 因为 |
|---|---|
| 「这页是给搜索流量用的落地页，还是内部工具页？」 | 内部页缺 description 无所谓，落地页缺就是大问题 |
| 「这批页面是同一套模板生成的吗？」 | 决定是逐页报还是模板层报 |
| 「有没有别的同类页面可以一起测？」 | 判断模板层的唯一办法 |

不值得问的：「你想检查哪些方面」（脚本一次全查完，没得挑）、
「要不要生成报告」（要，不然叫你来干嘛）。

## 六、报告结构

```
〇、结论一句话      ← 断在第几环、最该先改哪一条。让人只读这一行也知道该干嘛
一、页面概况        ← 查到的事实
二、规则判定（N 条） ← 每条按 ID 从 rules-*.md 查「为什么 / 怎么改」
三、你的判断         ← 本文件第二节，每条标明依据的事实
四、先改哪几条       ← 本文件第三节的四维排序，带理由
五、没查的、查不了的  ← 边界，必须有
```

### 每条结论都要标依据等级

出处见 `diagnose-chain.md` 最后一节。三个等级：

| 等级 | 写法 |
|---|---|
| **直接观察** | 「观察到：响应头里有 `X-Robots-Tag: noindex`」—— 附原始值 |
| **合理推断** | 「推断：这是模板层问题（依据：测了 3 个详情页都命中同一条）」—— **依据必须写出来** |
| **证据不足** | 「无法判断：需要 GSC 数据才能确认这页收没收录」 |

**绝不编造数据。** 没测过就不要写「预计影响 60% 的页面」这种没有来源的推算。

第〇、三、四段是你的产出，也是这个 skill 相对于「跑个脚本」的全部价值所在。
第一、二段的数字和结论照搬，不要改动。
