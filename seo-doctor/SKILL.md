# SEO Doctor

**干活的是你。这个 skill 给你的是链路、规则和边界。**

抓页面、读 HTML、看响应头、开浏览器 —— 你自己会，不重复教。你缺的是：
**按什么顺序查、每项的判定标准、什么情况下不该报、以及结论该怎么标依据。**

## 核心：按搜索链路诊断，不是按清单打勾

一个页面从「存在」走到「有搜索流量」要过六道关，**任何一道断了，后面全部归零**：

```
1. 爬虫进得来吗    2. 抓到的内容对吗    3. 允许被索引吗
4. 页面够不够格    5. 有路径被发现吗    6. 实际表现如何
```

**顺着走，在第一个断掉的地方停下 —— 那就是答案。** 后面的环节不用查，
查了也没意义：一个被 robots.txt 挡住的页面，讨论它的 title 长度是浪费时间。

**每一环只有三种状态，没有第四种：**

| ✅ 通过 | ❌ 断了 | ⚠️ 证据不足 |
|---|---|---|
| 查了，且**看到了正面证据** | 查了，发现问题 | 没查成 / 查不了 / 信息不够 |

⚠️ **「没发现问题」不等于「通过」。** 抓不到 robots.txt 就是「证据不足」，
不是「爬虫可正常访问」。给了假绿灯，用户会去别处找病因，而真病因被绿灯盖住了。

**一个方法拿不到数据就换下一个**（web_fetch → 命令行 curl → 浏览器），
robots.txt 和 sitemap 都是纯文本，三种里通常总有一种能拿到。
都失败就如实说「三种方法都没取到」——
**绝不为失败编造原因**（「推测做了 JS 反爬」这种话在纯文本文件上根本不成立）。

**⭐ 开工先读 `references/diagnose-chain.md`。** 那里写了每一环查什么、
断在这里意味着什么、以及**从症状反查环节**的对照表 —— 用户说「这页搜不到」
或者甩来一句 GSC 的「已抓取——尚未编入索引」时，直接查表定位从哪一环开始。

> 「已抓取——尚未编入索引」和「已发现——尚未编入索引」只差一个字，
> 前者是内容问题、后者是内链问题，**药完全不同**。搞反了会白干几个月。

## 三条不能破的

**1. 每条结论标明依据等级。** 这是能不能被信任的关键：

| 等级 | 写法 |
|---|---|
| **直接观察** —— 你真的请求了、看到了 | 「观察到：响应头里有 `X-Robots-Tag: noindex`」，附原始值 |
| **合理推断** —— 从现象推出来的 | 「推断：这是模板层问题（依据：测了 3 个详情页都命中）」，**依据必须写出来** |
| **证据不足** —— 想知道但查不到 | 「无法判断：需要 GSC 数据才能确认这页收没收录」 |

**绝不编造数据。** 没测过就不要写「预计影响 60% 的页面」。

**2. 不打分。** 不要星级、不要百分制、不要「配置水平优秀」。开发拿到分数不知道
该动哪一行代码。要总览就给计数（「命中 3 条，阻断 0」）。

**3. 「没查的和查不了的」单独成段，不许省。** 省掉它，用户会以为全查过了。

**发报告前对着 `diagnose-chain.md` 最后的自查清单过一遍。** 尤其这两条：
前面下过结论的事，不能又出现在盲区里（自相矛盾）；每个 ✅ 背后都要有一句
「观察到：…」。

## 输入与输出

| 用户给什么 | 能查到哪几环 | 交付什么 |
|---|---|---|
| 一个 URL | 1~4 | 单页诊断：断在哪一环、每条的「为什么 / 怎么改」、优先级 |
| 站点首页 | 1~5 | 加上：可达页面清单、**孤儿页（sitemap 差集）**、内链结构、模板层共性问题、死链 |
| 一批同类 URL | 1~4 且能判模板层 | 按规则聚合（「`canonical-missing` 命中 18/20」）+ 模板层结论 |
| GSC 导出的 CSV | 6，并能反查 1~5 | 收录率、15 类未收录原因归类、机会词，以及**从数据反查到代码根因** |
| 代码 / 模板文件 | 定位到文件 | 指出该改哪个文件的哪一段（**不代写代码**） |

**不交付**：SEO 评分、关键词研究、外链分析、排名查询、修复代码。

## 定测哪些页

| 用户给的 | 怎么做 |
|---|---|
| 一个具体 URL | 测它，测完**主动提议**再测一个同类页 —— 判断模板层的唯一办法就是测多页 |
| 一个站点 | **不要只测首页**，它往往单独写、最不具代表性。抓首页从链接里挑**列表页**和**详情页**各一个，三个一起测。详情页最重要，SEO 流量主要落在那里 |
| 一批 URL | 逐个测，**按规则聚合**输出，不要按页面罗列 60 条 |

## 两个现成的工具

### 单页 —— 覆盖环节 3、4 的一部分

```
node "<CUSTOM>/seo-doctor/run.js" --mode check --url "{URL}"
```

把整页 HTML 压成「页面概况」（title 原文与**显示宽度**、description、canonical、
lang、viewport、Open Graph、地标、图片/链接统计、ld+json 类型、标题层级大纲），
并把 21 条有明文标准的判定算好。

### 全站 —— 覆盖环节 5

```
node "<CUSTOM>/seo-doctor/run.js" --mode crawl --url "{站点首页}"
```

模仿 Googlebot 第一波抓取：从首页 BFS，**只跟服务端 HTML 里的 `<a href>`**，
遵守 robots.txt。自动产出：

| 产出 | 回答什么 |
|---|---|
| 可达清单（深度、来源页、锚文本、入链数） | 从首页点几次能到？谁在链它？ |
| **sitemap 差集** | 哪些页只在 sitemap 里、一条内链都没有 —— **孤儿页** |
| 按规则聚合的批量体检 | 命中 18/20 页 = 模板层问题，改一处修全站 |
| 内链结构 | 死胡同、入链薄弱、只被 nofollow 指向的页 |

顺带捞到单页检查看不见的：**死掉的内链**、**指向重定向的内链**。

参数：`--max-pages 200` `--max-depth 3` `--concurrency 3`。两个模式都支持 `--json`。

### 这两个工具的边界

**用它们是为了省事，不是它们权威。** 52 KB 的页面直接读进上下文既贵又容易看漏，
几百次请求靠工具调用做不来 —— 这两件事交给它们，剩下的自己查：

- **环节 1、2** 基本靠你 —— 尤其环节 2 必须用浏览器对比渲染前后
- **环节 5 有一半靠你** —— 爬虫不执行 JS，所以**按钮式跳转、分页器、列表项**
  这三种 JS 跳转它一个都看不到。要用浏览器**真的点一下**看 URL 变不变
- **环节 6** 完全靠 Search Console —— 见 `references/gsc-navigation.md`。
  ⚠️ **只读**：只看、只导出，绝不提交 sitemap、绝不请求编入索引

有一件事值得依赖它们：**长度按「半角当量」算**（全角字符算 2）。Google 按像素宽度
截断而不是字符数，人工数字符会两头都错。

## 规则明细

| 清单 | 对应环节 | 内容 |
|---|---|---|
| `references/diagnose-chain.md` | **主线** | 六环诊断链路、症状反查表、证据分级 |
| `references/rules-indexing.md` | 1、3 | robots.txt 匹配算法、meta noindex、**X-Robots-Tag 响应头** |
| `references/rules-meta.md` | 3、4 | title / description 长度、canonical、lang、viewport、og |
| `references/rules-semantic.md` | 4 | h1、标题层级、img alt、空 href、假链接、锚文本、地标 |
| `references/rules-schema.md` | 4 | ld+json 语法、Google 富媒体必填字段 |
| `references/gsc-navigation.md` | 6 | Search Console 怎么取数、只读边界、界面改版了怎么办 |
| `references/gsc-analysis.md` | 6 | 15 类未收录原因 → 六环映射、和前五环交叉验证、五个数据陷阱 |
| `references/review-guide.md` | — | 优先级怎么排、模板层怎么判、什么时候该追问 |

**每条规则的「已知边界」栏必须读。** 判定条件你自己也能想出来，但下面这些是
踩过才知道的 —— **误报是这类工具的头号死因**，报几次假问题就再没人用了：

- `alt=""` 不是忘了写，是装饰图的**规范写法**
- `href="#section-id"` 是合法页内锚点，只有光秃秃的 `#` 才算空链接
- canonical 去掉 `utm_source` 是**正当用法**，去掉 `page=2` 才是真错误
- robots.txt 返回 **404 等于全站放行**（常态），5xx 才要报
- `X-Robots-Tag: max-image-preview: none` 里的 `none` 是**值**不是指令，
  当指令读会凭空报出一条「阻断收录」
- robots.txt 挡住 + 写了 noindex = **互相抵消**，爬虫读不到那条 noindex

报告文案也从清单里取，不要现编 —— 现编会让同一条规则每次说法都不一样。

## 排优先级

清单里的「阻断 / 警告 / 建议」是**规则本身的通用级别**，不看页面类型、不看波及面。
真实优先级按四个维度重排（**上一条能分出胜负就不看下一条**），方法见 `references/review-guide.md`：

**1 断在越靠前的环节越优先**（环节 1 断了，环节 4 的问题不用谈）→
**2 模板层 > 单页**（一条命中 = 全站命中）→ **3 阻断收录 > 影响点击率 > 影响理解** → **4 同等收益先做便宜的**。

## 网络访问说明

`run.js`（本 skill 唯一的可执行文件）的行为：

| | |
|---|---|
| 请求什么 | **只请求 `--url` 显式传入的那个地址**及其重定向目标 |
| 请求方法 | 只有 GET |
| 内置域名 | **没有**。不传 `--url` 就一个请求都不发 |
| 携带凭证 | **不带**。不发 cookie、不发 Authorization、不读任何本地凭证 |
| 遥测上报 | **没有** |
| 结果去向 | 只打到标准输出。**全文件没有一处 `fs`**，不写盘、不外发 |

你自己用浏览器 / web_fetch 做的查证不在此列，走平台的工具权限。

## 关于 lib/vendor/cheerio.js

HTML 解析库 cheerio 经 esbuild 打包压缩后的单文件。打包而不声明 npm 依赖，是因为
平台导入时先 `npm install` 再扫描，扫描有 500 文件上限 —— 声明一个 cheerio 依赖
会装出一千多个文件，直接导入失败。

压缩文件会被扫描器报一条 `LOW_ANALYZABILITY`（可分析性偏低）。它报的不是安全问题，
是「这个文件我没法逐行审计」。**不要为此关掉压缩** —— 实测摊开成源码后几万行第三方
代码会撞上扫描器的正则，告警从 5 条涨到 24 条、最高级别从 HIGH 升到 CRITICAL，
全是函数名撞车的误报。
